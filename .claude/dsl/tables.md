# DSL reference: Tables (build-time ROM lookup)

The map of every page is `.claude/rules/dsl-reference.md`. **On this page** has a line for each
verb here; the entries after it tell each one in full.

## On this page

- `table :name, array` → `Table`, ROM data read by index; `data_pack`, from a copy
- `table_groups :levels, { 0 => [:forest], 1 => [:cave] }` → a handle whose `load n` brings one group of tables in: data bigger than the console holds
- `shell_screen do |first| … end`: a shell's first screen, its font, colours, picture, words and lines

## In full

- `table :name, ruby_array, width: :half, signed: nil` → a `Table`: a build-time Ruby array shipped as read-only ROM data, read at run time by a Value index. `t[i]` → a `Value` (like reading an Array the game changes, but read-only, from the cartridge); `length` is a build-time Integer. `width:` is the element size (`:byte`/`:half`/`:word`); `signed:` is inferred from the values (any negative → signed) unless you set it. An out-of-range index is made safe: a power-of-two table wraps it (what an angle wants), any other size clamps to the ends — and **the length you pick decides what a read costs**, because wrapping is one step and clamping is a test against each end, about twice the work. A length like 256 or 512 is the cheap one; round a sine table up to it and the reads get cheaper for nothing. Precompute what the console can't do cheaply each frame — a sine or reciprocal/distance table (see `examples/raycaster.rb`). A value that doesn't fit the width is a friendly build error. **A read is not free** — reaching an element costs about three plain steps, so a table read in a hot loop is real work rather than the single load it looks like. **On the Game Boy Color a game can keep as many tables as the cartridge holds.** Only 16K of the cartridge is always in view, so a table of a kilobyte or more is kept in the cartridge's banks, and in a game whose tables still do not fit, shorter ones go there too, the longest first. Reading a banked table puts its bank in view and puts the old one back, which costs a few dozen more instructions a read. A table a list is copied from with `copy_from` stays in view.
- `table_groups :levels, { 0 => %i[forest_map birds], 1 => %i[cave_map birds] }` → a `TableGroups` handle: **the game's tables in numbered groups, one group loaded at a time**, for a game whose data is more than the console holds at once — a level's map, its enemies and its sounds' numbers, kept apart from the other levels'. `levels.load level` loads the group a number names (a number, a variable or an expression; a fraction is a friendly error), in place of the group that was loaded. A table in no group is there the whole time. A table can be in more than one group of a set (the birds above), and in one set only (a friendly error names both sets). **A table in a group can be read only while a group holding it is loaded**: no group is loaded until the game loads one, a number naming no group leaves none loaded, and reading a table at any other moment stops the game with an error naming the table, its groups and the `load` to write — on every build, since on a console that holds one group at a time the table's place holds another group's numbers. `copy_from` counts as a read. A group naming a table the game never declares is a friendly error once the game is built. **What it costs**: on a cartridge (the Advance, the Color, the Super Nintendo, the Genesis), and as C, JavaScript or Ruby, every table is in reach the whole time, so `load` builds nothing and the cartridge is the same as without the groups. **On a PlayStation the build makes a disc**, an image of its sectors (`.bin`) and the cue sheet an emulator opens (`.cue`), in place of the program alone: each group is kept on the disc, and each set of groups has one room in memory as big as its biggest group, so the 2 megabytes hold the program and the biggest level, not every level. `load` reads the group into the room at the drive's double speed, 150 sectors of 2K a second (about 300K a second, a level of 1MB in three and a half seconds), as the console's own games read a level: the game waits while it reads, the music and the pads go on, and the pass that loads takes that many frames. Loading the group that is in already reads nothing, so `levels.load level` on every pass costs a test and a jump. Only tables go in groups: a game's pictures and recordings are kept in the program as before. A game that never says `table_groups` builds the same program it did without it. Worked example: `test/all/vblank/builder/test_table_groups.rb`; a game of more than 2 megabytes played from its disc: `test/lowering/ps1/vblank/ir/backends/ps1/test_ps1_table_groups.rb`.
- `data_pack from: ORIGINAL, version: "1.0" do |slots| … end` → a `DataPack`: slots of colours, tiles, numbers and pixels (pictures of up to 256 colours, one byte a pixel) from the player's copy of a retail original, made into a data pack as the game is built. `table :speeds, pack[:speeds]` and `image ..., colors: pack[:palette], places: pack[:walls].tile(0)` read a slot; the game holds only handles. The whole story is `.claude/dsl/original.md`.
- `shell_screen do |first| … end` — **the first screen of the game built as a shell, made the game's own**: the screen a player sees until their copy of the original has been read (the title, what the game needs, LOAD ROM and SETTINGS). `first.font`, `first.title`, `first.needs`, `first.labels`, `first.colors`, `first.picture` set how it looks, and `first.line "CREDITS", shows: :credits` adds a line that shows a scene and comes back. The block is a program of its own: its font, picture and scenes are declared inside it, and nothing in it may come from the data pack. A cartridge holds nothing of it, and a game that writes none gets VBlank's screen. The whole story is "The first screen" in `.claude/dsl/original.md`.
