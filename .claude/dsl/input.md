# DSL reference: Input

The map of every page is `.claude/rules/dsl-reference.md`. **On this page** has a line for each
verb here; the entries after it tell each one in full.

## On this page

- `held(:left)`, `pressed(:start)` (`:any`). Buttons `a b select start right left up down r l`, and `x y` on the Super Nintendo.
- `held(:left, player: 3)` (1 to 16, or `:any`); `players: 1..4` on `VBlank.game`; `most_players`; `drawing_for_local_player { |me| … }` → draw for this player alone, `mark over: hero, with: :arrow` there; `players_connected` → how many now. `vblank run --host` / `--join`: a match.
- `rumble frames: 12, pattern: "##..##.."` — shake a cartridge with a motor (the Color's).
- `computer_keys a: :d`, `computer_gamepad a: :west` — more keys and gamepad buttons for a button on a computer, beside VBlank's own.

## In full

- `held(:left)` — 1 while down; `pressed(:start)` — 1 on the press edge only. Use with `if`. Buttons: `a b select start right left up down r l`, and `x y` on a Super Nintendo; a button the console lacks is a friendly build error. A computer's window has no keys for `x` and `y` yet. The old `if_held(:a) { }` and `if_pressed(:a) { }` are a friendly error naming `if held(:a)` to write.
- **A name set from a button keeps that line's answer, as a Ruby local does.** `advance = pressed(:a)` while setting up, read in a `func` or the `game_loop`, keeps the press of the moment the game started, which is none, so it never changes. Write `pressed(:a)` where it is used, in the routine or the loop. A name set in game code is set again each pass and reads that pass's buttons. `held`, `players_connected`, a `clock` reading and a timer's `ticks` are the same. Tests: `test/all/vblank/dsl/test_plain_ruby.rb` (`test_a_name_set_up_from_a_press_keeps_the_press_of_its_line`).
- `held(:any)` / `pressed(:any)` — **any button at all**, which is how a game leaves an attract screen, a splash or a cut scene: `mode = :title if pressed(:any)`. `pressed(:any)` is true on a frame some button went down, the same edge each button has on its own — so A pressed while LEFT is still held counts, and a button held on and on is one press. It is one test against all ten buttons, cheaper than the ten `held` tests joined with `||` it replaces, and none can be left out. `:any` is not a button: a test's `hold(...)` and the command line's held keys refuse it, since holding "any" means nothing.
- `held(:left, player: 3)` / `pressed(:start, player: 2)` — **another player's controller**, from 1 to 16. `player: :any` is every connected player, so `pressed(:start, player: :any)` lets anybody leave a title. `:any` as the button works with it, `pressed(:any, player: 2)`. A number that is not a player (`0`, `17`, `:third`) is a friendly error at the line. Only a number written in the game: a player number worked out as the game runs is not taken yet, so a game for four writes the four, or a Ruby loop at build time (`places.each.with_index(1) { |x, p| x.increase!(1) if held(:right, player: p) }`, `places` a list of `var`s).
- **How many each console seats.** Game Boy Advance and Color: one controller, so `player: 2` and more are refused at the build in plain words, and `player: :any` reads that one. Super Nintendo: two (a Multitap is not read yet). Sega Genesis: one (the second pad is not read yet). A build that plays on a computer (C, a web page, Ruby): the desktop build, the browser build and the Ruby build (`vblank run`) all read sixteen. Sixteen is the computer's ceiling: it catches a typo, and the buttons of one pass stay one small list a network can carry, 32 bytes a pass. Each console's page says the same.
- `players: 4` on `VBlank.game` (or `VBlank.build`) — **how many players the game takes**: `4` is 1 to 4, `2..4` at least 2 and at most 4, and by console, `players: { snes: 1..2, computer: 1..8, else: 1 }`. A key is a console's name, `computer:` (any build that plays on a computer, whichever console it is made as) or `else:` (every build the rest do not name); a computer build reads `computer:`, then its console's, then `else:`. Then a line that reads a player past the most is a friendly error, and a console that cannot seat the most refuses the game at the build, even where no line names the last player yet (a game that reads `player: :any` would lose players quietly otherwise). Saying nothing is fine: the game reads whichever players its lines name, and each console refuses what it lacks. The fewest is kept for a joining screen; nothing reads it yet. Errors: a count that is not 1 to 16, a range backwards, a key that is no console, a console the game is not for.
- `most_players` → a Ruby number while the game is built, **the most players this build seats**: the top of what `players:` says for it (`players: { computer: 1..4, else: 1 }` gives 4 in a build for a computer and 1 on a cartridge). The game says its players once and lays its seats out from this, so the two cannot drift apart: `walkers = (1..most_players).map { |player| sprite :walker, at: [20 * player, 80] }`. It is like `screen_width`, a number for the build and not a variable the game keeps. A game with no `players:` has no number to give, and `most_players` is a friendly error telling it to say one.
- `drawing_for_local_player do |me| … end` — **what only this machine's person sees**, in a match played over a network. Every machine of a match runs the whole game from every player's buttons, so a number that differs between machines must never reach what the game remembers, or the machines drift apart and the match stops. Which player this machine's person is (`me`, from 1) differs by design, so it is given out in this block only, and the block may only draw: `drawing_for_local_player { |me| draw_text "YOU #{player}", 8, 8, :white if me == player }`. **How the build holds a game to that**: every statement in the block must be a drawing one (or an `if` around drawing ones, with the declarations drawing needs), so a variable, a list, a pool, a call, a sound and a random draw in it are refused where they are written, naming the line; and `me` is refused anywhere outside such a block, even kept in a Ruby array and used later, once the whole game is built. What is drawn on one machine and not another changes the picture and nothing the game keeps. **Where it works**: it builds on every console, where `me` is 1 (a cartridge has one person); a match is played on a computer's build. A block that draws on a `screen :tiled` follows that screen's rule: text and sprites are declared once, above the `game_loop`, and a text line can be shown only under an `if` on `me`. A picture that moves with the player's sprite is a `mark` (next). **In a test**, `Reference#local_player = 2` says which player the interpreter's person is. Worked example: `examples/wanderers.rb` (an arrow over this machine's walker); `test/all/vblank/builder/test_local_view.rb` (what is refused), `test/lowering/ruby/vblank/network/test_local_view_in_a_match.rb` (four machines agree).
- `mark over: sprite, with: :picture` (`offset: [dx, dy]`) → `Mark` — **a picture shown over a sprite, with no place of its own**: centred just above the sprite, moved `offset:` from there, shown while the sprite is shown and while the `if`s it is written under hold. It is how one machine of a match marks its own player: `drawing_for_local_player { |me| walkers.each.with_index(1) { |w, player| mark over: w, with: :arrow if me == player } }`. **Why it is safe in a match**: its place and whether it shows are not variables. The console works them out on every frame from the marked sprite's own place and the `if`, so nothing about a mark is part of the game state each machine checks, and `me` in it is held to the block by the same check as any drawing. **What it refuses**: `move`, `move_to`, `x`, `y`, `show` and `hide` on the `Mark` are friendly errors (move the sprite; put an `if` around `mark`). The sprite must be one the console shows (any sprite on a `screen :tiled`, or `over_picture: true` on a bitmap); a bitmap game can also `blit` at the sprite's place. **Cost**: one more sprite of the console's; a game without `mark` builds the same bytes. It works outside a match too (a label over a boss). Write it where sprites are declared, above the `game_loop`. Tests: `test/all/vblank/builder/test_local_view.rb`.
- `players_connected` → a `Value`, **how many players are connected now**, at least 1. A player counts from the first time one of their buttons is down, and stays counted: letting go of every button is not unplugging. Ask it before waiting on a player, so a game never reads a missing player as idle: `draw_text "P3 PRESS START", 40, 80, :white if players_connected >= 3`. A console that reads one controller answers 1. The Super Nintendo's cartridge build does not make it yet and refuses it by name (it cannot yet tell whether the second controller is plugged in: wait for a button on it instead); a build of the same game for a computer answers it.
- **In a test or a tape**, another player's buttons have the player's number in front: `hold(:left, :p3_left)`, `:p2_start`, up to `:p16_a`, in `hold`, `input_each_frame`, a script and a tape. Holding `:p3_left` once makes three players connected from then on. **Where the buttons go**: the interpreter keeps the names; a computer's runtime is handed one number per connected player each pass, the first player's first, a bit a button — the plain list a network will carry later. A console reads its own controller ports. A game that never names a player past the first builds the same bytes as before. **What a person presses on a computer** (the desktop window, `vblank run` and the web page alike), in a game whose `players:` seats two or more on that build: the keyboard is player 1, and its right hand is player 2: `I J K L` the pad, `O` is A, `U` is B, `7` and `9` are L and R, `8` is Select and `0` is Start. Each gamepad (a controller on the web page) is one player: the first one plugged in is player 1, beside the keyboard, the second player 2, and so on; a gamepad keeps its player while it stays plugged in, and one plugged in takes the lowest player no gamepad has, so pulling out player 2's and plugging it in again gives player 2 back. Players 3 and 4 are gamepads only: four people do not fit round one keyboard, and most keyboards lose keys when that many are held at once. Player 2's keys are only those nobody else has: a key a player chose for player 1 or a hotkey in the settings file stays theirs, and a web page given a `keyMap` of its own has none. A game that seats one player, or names no `players:`, plays as it always did: every gamepad and key is player 1's, so name `players:` to give a computer's players their own gamepads and keys. In a match over a network every gamepad and key at a machine is that machine's one player. A game whose `players:` seats two or more cannot add player 2's keys with `computer_keys` (a friendly error). The desktop window's `--help` and the web page's key words name player 2's keys for such a game; `vblank run --help` does not yet. Tests: `test/lowering/native/vblank/ir/backends/native/test_native_seats.rb` and `test_native_desktop.rb`, `test/all/vblank/live/test_seats.rb`, `test/lowering/js/vblank/ir/backends/js/test_js_page_players.rb`. Worked examples: `examples/wanderers.rb` (up to four players walk a tiled map, each in a colour `rand` picks as they join; `players: { computer: 1..4, else: 1 }` with `most_players` makes four walkers on a computer and one on a cartridge, and `players_connected` hides the seats nobody has taken; its four-player tests are `test/wanderers_tests.rb`), `test/many_players_tests.rb` (four markers and a crowd of sixteen, played on the interpreter and as C, JavaScript and Ruby, each by a file in its run's folder that includes it), `test/all/vblank/builder/test_player_option.rb` (what each console refuses).
- **A match over a network** — `vblank run game.rb --host [PORT]` on one computer and `vblank run game.rb --join HOST:PORT` on another play one match of a game, as Ruby, each person with their own window. **How it works**: every computer runs the whole game, and they send each other only each player's buttons for each pass (lockstep, `Network::Lockstep`). A computer runs a pass once it has every player's buttons for it, so one slow computer slows all of them and changes nothing in the game. A press waits `--input-delay` passes (2 unless said) before the game uses it, the same on every computer, which gives the network that long to carry it. Every few passes each computer sends a short number (a CRC-32) for the whole game state, and a computer that finds two numbers differ stops with the first pass that differs and the tape of the match (`Network::Desync`). The host picks the match's seed, which is added to the game's random numbers once the game has set itself up, so the colours `rand` picks differ from match to match and agree within one. **What a game needs**: `players:` for a computer (`players: { computer: 1..4, else: 1 }`), since the host cannot seat more players than the game takes, and `--players N` says how many this match has (2 unless said). The host is player 1, and the others are numbered as they join; players join only before the match starts. Every computer must run the same game file built for the same console: the host refuses a game, a build or a console that differs, and says which in plain words (`Network::Refused`). **A player who goes** (closed the window, or the program was killed) leaves on the same pass on every computer, and nobody waits for them: the window's title says "Player 2 left the match." and the game goes on. If the host goes, the others go on alone. **What differs between computers and what does not**: `frames_since_power_on` and `once_a_frame` count passes, `randomize` stirs the shared stream, and a match has no clock (`clock.present?` is false); which player this computer is can only be drawn (`drawing_for_local_player`). **With no window**, `--no-window --pictures N --keys right` plays a match with nothing but the keys named held, which is how a test, or a computer with no screen, plays; the command prints what the match said as it said it. The messages are in `docs/network/protocol.md`. **Through a relay**: `--relay [URL]` makes a match meet on a relay, so nobody opens a port: with `--host` the command makes a room and says its code, and with `--join CODE` it joins that room. The relay's address is one setting: the URL given to `--relay`, or the `VBLANK_RELAY_URL` variable (`Network::RelayPlay`); there is no default yet, since the real relay has no address. The connection is a WebSocket written in Ruby (`Network::WebSocket::Client`: the handshake, frames, ping and close, over `ws://` or `wss://` with the relay's certificate checked), since Ruby has none. **In JavaScript** the same session is `rg_lockstep.js` (`RgLockstep`), which a node copy plays through `--match-host` / `--match-join` and a test carries the messages of (`test/node_copy.rb`): a node copy and a Ruby copy of one game carry one fingerprint and one state number on every pass. Through a relay it makes or joins a room with `rg_relay.js` (`RgRelayTransport`, over `RgWebSocketLine` in a browser, since a browser can open only a WebSocket); a node copy takes `--relay-make` or `--relay-join CODE`, and a test carries its line to the stand-in relay. A page driver for either is not built yet. **A relay to try it on**: `ruby tools/stand_in_relay.rb [PORT]` runs the stand-in relay as a program and says its address. A connection by address (`Network::DirectPlay`) needs no relay: the host runs the same room itself (`Network::DirectRoom`). Tests: `test/lowering/ruby/vblank/network/` (`test_lockstep.rb` for two to four copies in one process under every delay; `test_direct_play_command.rb` for two processes, one killed).
- `rumble frames: 12, pattern: "##..##.."` — **shake the player's hands**, as a ball hitting a bumper does. The motor runs for `frames:` frames (0 to 65535), on or off on each by the pattern: eight frames, `"#"` on and `"."` off, read from the left and round again after the eighth. Steady by default; `"#.#.#.#."` is a light buzz. A number 0–255 is read as the Color's own games read theirs — turned a bit to the right each frame and the lowest bit read, so its frames come from bit 1 up to bit 7 and then bit 0 — and a pattern taken from one of them (Pokémon Pinball's `wRumblePattern`) plays the same. A rumble said while one runs takes its place, and `frames: 0` stops it. It starts on the frame after the pass that says it, and moves on with every frame shown, a slow pass's too (Pokémon Pinball counts its rumble down a pass at a time instead, which is the same while the game keeps up). A game that halts stops the motor. **Where it is felt**: on a console whose cartridge carries a motor — the Game Boy Color's, whose cartridge then says so in its header. On any other it does nothing, and the game plays the same (see each console's page). A Color cartridge with a `clock` has no motor, so a Color game that uses both is refused. **In a test**: `motor_on?` on the interpreter, a checked run and the emulator's reader says whether the motor runs on the frame shown; the checked run compares it on every pass. **What it costs**: on the Color, a few bytes of work memory, a short routine each frame shown, and two writes where it is said; a game that never says it builds the same bytes. Worked example: `test/all/vblank/builder/test_rumble.rb`, `test/lowering/gbc/vblank/ir/backends/gbc/test_gbc_rumble.rb`.
- `computer_keys a: :d` and `computer_gamepad a: :west` — **more keys and gamepad buttons for a button, on a computer**: the desktop window, `vblank run` and the web page start with VBlank's own layout (the arrows, X for A, Z for B, Return for Start, Backspace and Right Shift for Select, A and S for L and R) and these besides. Nothing is taken away. Each takes the buttons as keywords, one name or a list each: `computer_keys a: :d, start: %i[space]`. A key is a letter (`:d`), a digit (`1`), or one of `:space :enter :backspace :tab :escape :minus :equals :left_bracket :right_bracket :backslash :semicolon :quote :backquote :comma :period :slash :up :down :left :right :left_shift :right_shift :left_ctrl :right_ctrl :left_alt :right_alt`; a gamepad button is one of the four the layout leaves free, `:west :north :left_stick :right_stick`. A game names its keys in one line and its gamepad buttons in one line. **No key presses two buttons**, so these are friendly errors at the build: a key the layout already gives a button (the right arrow is Right, so `computer_keys a: :right` is refused, since taking it would leave Right without it on the menus; give A a key of its own, such as `:d`), a key the window keeps (P, N, M, F, Tab, Escape, the key above Tab), one of player 2's keys (`I J K L O U 7 8 9 0`) in a game whose `players:` seats two or more, one key for two buttons, more than a button has room for (two keys and two gamepad buttons, counting VBlank's; Select has its two already), and a button the window has no keys for (`x`, `y`). **What a player sees**: Controls shows the game's keys beside VBlank's (`X, D / east, west`), a player can change any of them, and Reset puts the game's layout back, not VBlank's alone. The settings file and the web page's kept settings never hold them, since one file serves every game: they are added again each time the game starts, wherever the player has not given the key to something else. A page that hands `createGame` a `keyMap` of its own and no menu gets that map and VBlank's controller buttons alone; with the menu on, the player's settings decide the keys as above. **Where it applies**: builds that play on a computer; a console's cartridge is built byte for byte as without it, and a game that names none builds the same tables as before. Tests: `test/all/vblank/builder/test_computer_controls.rb` (what is refused, the cartridge unchanged), `test/lowering/native/vblank/ir/backends/native/test_native_window.rb` and `test_native_desktop.rb` (the desktop window), `test/all/vblank/live/test_settings.rb` and `test/lowering/ruby/vblank/ir/backends/ruby/test_live_game_controls.rb` (`vblank run`), `test/lowering/js/vblank/ir/backends/js/test_js_page_menu.rb` (the web page).
