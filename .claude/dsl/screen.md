# DSL reference: Build / screen

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `VBlank.game "NAME", consoles: %i[gba] do … end` — **every game names the consoles it is for**: `%i[gba]` for the Game Boy Advance alone, `%i[gba gbc]` for the Game Boy Color too. A game that names none is a friendly error, since nothing is taken to be for the Advance, and `vblank build` (and `ruby game.rb` with `write_if_main`) makes a cartridge for each console named; `play`, `profile` and `compare` run one cartridge, so for a game of two they need `--console`. Besides that, **the name is all the cartridge needs from you.** A cartridge also carries a four-character code, and that code is the only thing an emulator has to tell one cartridge from another: it reads the code to put a title in its window, and it reads the same code to decide what save hardware the cartridge has — plain memory, flash, a chip read a bit at a time — and whether there is a clock or a rumble motor in there. So a code made up by hand is a real footgun, and not a cosmetic one: thousands of cartridges shipped and the memorable codes are long gone, so landing on one means the emulator reports somebody else's game AND fits somebody else's save hardware — which it puts in place of the one your cartridge asked for, so a game that saves can stop saving with nothing on screen to say why. The framework works a code out from the name instead, starting with a letter no cartridge ever used, so nothing in the program mentions any of this. `code:` and `maker:` are still there for a game that wants its own — and a code a real cartridge already carries is a friendly error, naming the free letters (D, E, H, I, L, N, O, Q, T, W, Y). The maker is the two characters that name a publisher, and a game that says nothing says it has none, which is true: `01` is Nintendo's. **`stack_room:`** (also on `VBlank.build`) is how many bytes of the console's 32K quick memory the game's stack is given — the room where every routine keeps where to return to. Left out, the build gives it 1024 bytes, many times what any game here was measured to use (56 at most), and more for a game whose calls nest deeply, worked out from the program; a game can say more for safety or less for room. Every byte held for the stack is one its variables, lists and code cannot have, and a stack that outgrows its room writes over them with nothing to say so. It is a number of bytes, a multiple of 4, from 64 to 16384; anything else is a friendly error. **`code:`, `maker:`, `stack_room:`, `fast_cartridge:` and `fast_code:` are the Game Boy Advance's alone** (`Cartridge::AdvanceBuild::SETTINGS`): a game for both consoles says them once and its Color cartridge is built without them, and a game or a build for the Color alone that says one is a friendly error rather than a setting quietly dropped. **`menu: false`** leaves out the menu a window played on a computer opens over the picture (F1 in `vblank run`); a game has one unless it says not. It changes nothing in a cartridge. **`players:`** (`4`, `2..4`, or by console) says how many players the game takes; see `.claude/dsl/input.md`.
- `screen :bitmap` — pick the display. **A game that never says `screen` is on `screen :bitmap`**, exactly as if that were its first line, on every backend: the build switches the bitmap screen on at boot, so `pixel`, `fill_rect` and the rest show up with nothing else written. Not a warning and not an error — it is the default. Say `screen :bitmap` anyway when a reader would want to see it. `screen :bitmap, tear_free: true` = double-buffered (Mode 4). `screen :tiled` = tile backgrounds + hardware sprites (also decides which kind `sprite` makes). `screen :rotozoom` = a background that can turn and resize as one whole piece — a title screen that zooms in, a race track that spins and pulls away — instead of only scrolling straight the way `screen :tiled`'s layers do. See `background(...).rotate` / `.scale` under Tiled backgrounds. **A `screen :tiled` background can turn and resize too, and that is the arrangement nearly every game wants**, because a turning layer is almost never the whole picture: a title where an object flies at the player over a backdrop, a map screen that spins inside a fixed frame, a road that banks under a sky and a status bar. Nothing in the program says so — a background is one that turns because the program turns it, and the build picks the hardware that holds what was declared. **What it trades is scrolling layers**: `screen :tiled` gives four of them while nothing turns, and two of them beside a layer that does. **That trade is per SCREEN, not per game** — the console is told which arrangement it is in by one register and can be told again whenever the screen changes, so a title screen with something flying at the player over two scrolling layers can hand over to a game with four scrolling layers and nothing turning, in one cartridge. Declare each scene's backgrounds inside that scene and the build works the arrangement out per scene; nothing in the program names one. **That is four AT ONE TIME, not four in the whole game** — a background declared inside a `scene` is up only while that scene is, so scenes take turns with the layers and a game may declare four in each of as many scenes as it likes (see "A scene owns what it draws" under Scenes & funcs). Asking one screen for more than fits is a friendly error naming both counts and the scene that ran out, never a layer quietly left undrawn. So reach for `screen :rotozoom` only for a screen that is nothing BUT a turning layer — it is a third arrangement again (one background, no scrolling ones at all); a plain scroll on it is a friendly error pointing at `rotate`/`scale` instead.
- `screen :bitmap, tear_free: true, late: :show_now` (or `late: 40`, or `late: :wait`, the default) — **what the tear-free screen does with a page the game finished too late** for the break between pictures it was meant for. By default it waits for the next break, so the picture never tears, but a pass that runs a little over its frame then costs a whole frame: a game at sixty drops to thirty for it, and a player feels the hitch. `:show_now` shows such a page as soon as it is done, so a frame is only as late as it really is, and on those frames the picture can tear — it changes part way down. A row number from 0 to 159 shows it at once only while the screen is still sending the picture above that row, where a tear is least seen, and waits otherwise. A page finished during the break itself is shown at once by either, because nothing is being sent then and nothing can tear. **`pace:` says what late means**: the pictures a second the game aims for, 60 (the default), 30, 20 or 15, and a page is late when it misses the break that rate aims at. A game that runs at thirty and says `pace: 30` is on time on every pass that fits two frames, so it never shows those at once and never tears for them; only a heavy pass that runs into a third frame is shown at once, which keeps it at thirty where waiting drops it to twenty. Left at 60, a game at thirty is late on every pass, and `:show_now` then shows every page as soon as it is done — the most pictures a second, and a tear on most of them. **One tear does not set off another**: the pass after a page shown part way down starts part way down too, so it is late only for the break after the coming one, and a page it finishes in the coming break is shown there, where nothing tears. **It is said per `screen`, so per scene**: allow it while the game plays and keep a menu or a still picture from ever tearing; a scene with no `screen` line of its own does what the game's screen does, however the game reaches it. It changes when a page is shown, never what is on it, so the interpreter and the desktop and web builds draw the same game with or without it. `rom.profile` counts the pages it showed at once and how many of those were part way down the picture — which is what it cost, each a frame that may have torn — and counts them as new pictures in its frames a second. `late:` without `tear_free: true` is a friendly error, because only that screen keeps a finished page to show; so is a setting that is not one of the three, a pace other than 60, 30, 20 or 15, and `pace:` on a screen that waits.
- `screen :tiled, backdrop: :white` — **the colour the screen shows wherever nothing is drawn**: the cells a background leaves empty, the see-through pixels of its tiles, a scene with no background, and the frames before a screen's background is up. Black unless a screen says another, which is every game that says nothing, to the byte. Any colour name, or a colour (`rgb`), works. A game fading its first screen in from white says `backdrop: :white`, and its screen is white from power-on rather than black while its art is copied in. **Said at the top of the game it is the whole game's; said on a scene's own `screen` line, that scene's**, and a scene that says none shows the game's. A picture drawn from colours alone, with no place numbers, counts its black pixels as see-through, so they show the backdrop: mark see-through places with `:transparent` and keep black as a colour. `screen :rotozoom` takes it too. On `screen :bitmap` it is a friendly error, since a painted screen draws every pixel; use `clear_screen` there. **On the Game Boy Color a game has one backdrop**: the Color keeps it as the first colour of each of its eight colour lists, so a scene that says a backdrop other than the game's is refused there, and a screen of eight lists with empty cells needs one of them to hold the backdrop colour (black did that before, as most lists hold black). Worked examples: `test/all/vblank/builder/test_screen_backdrop.rb`, and for a scene's own, `test/console/gba/vblank/builder/test_screen_backdrop_on_the_advance.rb`.
- `screen :tiled, backdrop: :screen_colors` (also `backdrop_place: 2`) — **a backdrop that fades with the picture.** `backdrop:` takes the name of a `colors` list where a colour would go, the way `image ..., colors: :sea` and `draw_with :hurt` name one, and the backdrop is then that list's first colour, whatever the list holds: `recolor :screen_colors, walk, showing: step` fades the sprites and backgrounds drawn with the list and the backdrop together, **on the same frame**, through the same tint, with nothing more said. A console game's own fade works this way (a Genesis game points its backdrop at the first colour of a list and writes the list), and the backdrop then never lags its picture by a frame or stays lit on a screen gone black. **Why the first place by default**: a list's first place is its see-through one, the place a picture drawn from it never draws, and what a see-through pixel shows is the backdrop, so a list made for a screen's colours already has a home for the colour behind them. `backdrop_place:` picks any other place, counting from 0. **Why a name and not a new verb**: the backdrop is still the colour `backdrop:` says; naming a list only says where that colour comes from, and the list's `recolor` is the one line that changes it, so it changes exactly when everything else drawn with the list does. A list nothing recolours is its declared colour for good. **It is the whole game's backdrop**: say it on the game's own `screen` line, which must be the first one, after the `colors` line that declares the list. A scene arriving leaves the backdrop as the list has it, so a screen faded to black stays black across a hand-over. What is refused, each a friendly error at the line: a name that is no colour and no list, a list named like a colour (`colors :navy, ...`), a place the list does not have, `backdrop_place:` with a colour, the list named on any `screen` but the game's own, a scene's `screen` that says a backdrop of its own beside it, and any bitmap screen in the game (a bitmap screen has no backdrop). **Each console**: the interpreter and the desktop, web and Ruby builds change the backdrop where the list is told to hold another set. The Advance keeps its backdrop in the first place of the background colours, which no list's group can be, so the colour is copied there from a table of the backdrop's colour in each set, through any tint, and put back whenever the background colours are written again. The Genesis points its backdrop register at the list's own colour where the list keeps a palette and the place is one of its fifteen, and copies the colour into colour 0 otherwise (place 0 is see-through and no palette keeps it). The Super Nintendo copies it into colour 0. The Game Boy Color build does not make it yet and refuses it in plain words. Worked example: `test/all/vblank/builder/test_screen_backdrop_list.rb`.
- `screen :bitmap, tear_free: true, colors: [...]` — **say which colors the screen shows** instead of letting the framework work them out from the ones you name. The tear-free screen holds a number per pixel that picks a color out of a shared table, and normally the framework builds that table for you, silently, from the color names you write — which is right until your pictures come from somewhere that already decided. Art imported from another game or a paint program has pixels that are numbers picking out of *its* table, so give the colors in that table's order and the pictures line up. Everything else is unchanged: you still write color names everywhere, and you never write a slot number. **The order is the whole point** — nothing is moved, nothing is added (not even black, which the worked-out table always reserves at the front), and a color repeated in the list keeps both places, because dropping one would shift every color after it and move every pixel of every picture. Drawing with a color the screen was not given is a friendly error naming it; giving two screens different lists is a friendly error, because the display holds one table at a time; and `colors:` without `tear_free: true` is a friendly error, because a plain bitmap screen holds a whole color in every pixel and has no table to fill in.
- `screen :bitmap, pixel_size: 2` (also with `tear_free: true`) — **a painted screen whose pixels are shown twice as big.** The game draws a picture half the screen's width and half its height, 120×80 on the Advance, and the console shows each of its pixels as a square of four, filling the screen. Everything the game draws costs about a quarter of what it did, at a chunkier look, as the old first-person games did for speed: `examples/two_rooms.rb` built with `--set pixel_size=2` shows twice the pictures a second on the Advance. **`screen_width` and `screen_height` answer the small picture's size**, and every verb draws in its pixels; the interpreter plays the small picture, and the desktop, web and Ruby builds play it at that size. It is the whole game's (the program's `pixel_size`, which `Program#described_console` applies), so it goes on the game's first `screen` line, outside any scene, before anything reads the screen's size, and every later screen in the game is `screen :bitmap`; each of those is a friendly error, and so is a size other than 1 (the default, the screen as it is) or 2. **How the Advance does it**: the painted screen is its third background, the one that can resize, and the build tells it to step half a pixel for each pixel it shows, so the picture is shown bigger with nothing copied, exactly: two pixels of the screen are one of the picture's. Not mosaic, which shows blocks of a whole-size picture, so a game would still draw all of it. A whole-screen `clear_screen` fills only the rows that are shown. **Not made yet with big pixels, and refused by name on every console** (`Checks::BiggerPixelsNotMadeYet`), since each is counted in the console's pixels rather than the game's: the camera (`camera`, `shake_screen`), `pixelate`, a light (`spotlight`, `iris_in`, `iris_out`), a fade held to a rectangle, a sprite `over_picture: true`, `read_scanline`, and a game shown in a border. **Each console**: the Advance shows it; the Game Boy Color and the Genesis refuse it, having nothing that shows a pixel bigger; the Super Nintendo and the PlayStation refuse it as not made yet (their answers tables say so). Worked examples: `test/console/gba/vblank/builder/test_screen_pixel_size_on_the_advance.rb`, and the refusals in `test/all/vblank/builder/test_screen_pixel_size.rb`.
- `floors = setting :floors, 60` — **what this build was told**, for a game that comes in several cuts: which floors are in it, where the player starts, which screen it boots on. The default is on the same line; a setting with no default has to be given. It is a value while the game is BUILT, a plain Ruby value like the numbers a game works its tables out from, not a variable the game keeps while it runs. It is handed to ONE build — `game.program(settings: { floors: 1 })`, `game.build_rom(settings: …)`, `VBlank.build(…, settings: …)`, `vblank build game.rb --set floors=1`, or `write_if_main(settings: …)` on a game file's last line — so a test builds a one-floor cartridge beside a sixty-floor one, on another core at the same moment, and neither sees the other's. That is why it exists: reading the environment from inside the game's block reads something the whole process shares. The command line can only give text, and text is read as the kind of thing the default is (a number, a name, `true`/`false`); a setting with no default arrives as given. Three friendly errors: a setting the build gave that the game never asks for (a name spelled two ways would otherwise build the default and look right), a setting with no default that was not given (naming what was given instead), and text that cannot be read as its default's kind. Where a game still wants the environment, the line that builds it is the place to read it: `write_if_main(settings: { floors: ENV.fetch("FLOORS", "60") })`.
- `music = built_for_computer? ? 1 : 0` — **whether this build plays on a computer**, for a game that wants a different default there, with no second game file and no `--set` to remember. It is true for `vblank run` (with a person, a script or a tape at the controls, on every `--on` way), `vblank build --format` for the desktop, the web and Ruby, and `vblank preview`, and false for a cartridge. It is a value while the game is BUILT, a plain Ruby true or false, like `setting`, and not something the game can ask as it runs. `game.program`, a test's player and `walk.play(cartridge, on:)` get false, since they play the game to check the cartridge against it. A `vblank run` whose tape is written out for an emulator (`--write-mgba-script`, `--write-bk2`) is built with false too, so the run is the game the cartridge holds.
- `song(:theme) { … } unless built_for?(:snes)` — **whether this build is for a console**, for a game for several consoles that wants a choice of what each one's cartridge holds: music left out of one, a title line only a bigger screen has room for. A plain Ruby true or false while the game is BUILT, like `built_for_computer?`, worked out once before any of the game runs. It answers the console the game is built for, however it is then played: the game as C, in a web page or as Ruby built for the Advance answers `built_for?(:gba)`, as the Advance's cartridge does, so every way of playing it is the same game. `game.program(console:, variant:)`, `game.build_rom(console:)` and a test's player (`game.program(console: game_console)`) answer by the console they were given, the game's first console when given none. `built_for?(:snes, variant: :superfx)` asks about the variant too (`variant: :none` is the plain console); left out, any variant of the console answers true. Friendly errors: a console the game's `consoles:` does not name (no build of the game could answer true, so it is a misspelt name or a console not yet added), a console there is none of, and a variant the console does not have, each refused on every console's build. **Fitting one game to several consoles** is mostly not this: lay every place out from `screen_width` and `screen_height`, in one game loop, and the game fits each screen with no question asked; `built_for?` is for the few choices that are truly the console's. Worked example: `examples/everywhere.rb`, one file for the Advance, the Color, the Super Nintendo and the Genesis, whose Super Nintendo build is titled SUPER BOUNCE and holds no tune.
- `VBlank.game "NAME", consoles: %i[gba gbc] do … end` — **a game for the Game Boy Color as well as the Advance.** A game whose `consoles:` names `:gba` alone is for the Advance alone, and building it for a Game Boy Color (`game.program(console: :gbc)`, `game.build_rom(console: :gbc)`) is a friendly error naming both screens: a game laid out for 240×160 and shown on 160×144 loses a third of its picture, which no warning would make right. Saying `consoles:` is saying the game lays itself out from **`screen_width`** and **`screen_height`** — the size of the screen it is being built for, 240×160 or 160×144, read in the block like any Ruby number — rather than from numbers for one screen: `paddle_x = screen_width - 12`. Everything that already works from the screen does the same with no change: `:center` text, `clamp_to_screen`, `center_on_screen`, the edge tests, a grid checked against the screen. What each verb does on a Game Boy Color — works, or is refused naming the hardware it lacks and saying what to use instead — is `Console::ColorAnswers` (`lib/vblank/console/color_answers.rb`), and the reasons are in `doc/research/gbc-feature-policy.md`.
- `VBlank.game "NAME", consoles: %i[gbc gba], variants: { gba: :color_screen } do … end` — **a game laid out for the Game Boy Color, built for the Advance too, without a second copy.** A game for the Color alone (`consoles: %i[gbc]`) uses the Color's 160×144 screen, and building it for the Advance is a friendly error that names this fix. With the variant, the Advance build keeps the Color's screen: `screen_width` and `screen_height` answer 160 and 144 in it as in the Color's, the build checks lay the game out against that, and the interpreter plays it on a 160×144 screen. The Advance shows that screen at its own size in the middle of its 240×160 one, from (40, 8), with a border in the 40 columns at each side and the 8 rows above and below, which is what an Advance does with a Color cartridge (no whole-number scale fits). The game itself changes nothing. **The border stays put**: a background the game scrolls, a sprite it moves, a painted screen and its `camera` and `shake_screen` all move inside the game's screen, and whatever runs past its edge is behind the border. A whole-screen `fade` or `tint` darkens the game's screen and not the border. Without `border`, the build draws a border of its own: a dark slate with a black line and a lighter edge round the screen. **How the Advance does it**: the background scrolls and the painted screen's corner are moved by (40, 8); the sprites are written into a copy of the sprite table that is copied into the console's once a frame with (40, 8) added; the border is 32 sprites in the first rows of the console's table, in front of everything, whose pictures take the last 240 tiles of sprite memory and whose colours take the last group of sixteen sprite colours, which the game's own sprites cannot use; and the display's first window is the game's screen, inside which the blend applies. So the game has 32 fewer sprites (96 at once), and a sprite's pictures are kept in the half of sprite memory a painted screen never reaches, less the border's. **Not made yet in that build, and refused by name** (`Checks::BorderNotMadeYet`): a status bar, a light (`spotlight`, `iris_in`, `iris_out`), a fade held to a rectangle or under a layer, a background bent row by row or one that turns, `screen :rotozoom`, `pixelate`, `hide_sprites` and `read_scanline`. The desktop, web and Ruby builds of it (`--format`, `vblank run`) show the game's 160×144 screen in a window of that size, with no border, and play no Advance start-up. `vblank build --variant color_screen` asks for it for one build, and `--variant none` builds the Advance's plain cartridge. Worked examples: `examples/pong_gbc.rb`, and `test/lowering/gba/vblank/ir/backends/gba/test_border_sprites.rb`.
- `border from: "border.png"` / `border "#" => :blue, "." => :cyan do … end` — **the border round the game's screen, in a build that shows it in a border** (above). It takes what `image` takes (`from:`, `data:` with `width:` and `height:`, places, or text art), without a name, since a game has one border. It is a picture of the WHOLE screen, 240×160 on the Advance; its middle is never seen, because the game's screen is drawn there. A smaller picture whose width divides 240 and whose height divides 160 is repeated across the screen, so two lines of text art make a pattern. Friendly errors: a see-through pixel (nothing is behind a border), more than 15 colours (the border is drawn from one group of sixteen sprite colours, the first of them see-through), a size that does not repeat across the screen, and `border` said twice. A build that shows the game's screen whole (the Color's own, any other console's, or the Advance without the variant) draws no border and keeps nothing of it, so the game builds the same bytes there as without it; the colours and the transparency are still checked there, so a wrong border is heard about wherever the game is built. Worked example: `test/all/vblank/builder/test_border.rb`.
- `VBlank.game "NAME", consoles: %i[gba snes], variants: { snes: :superfx } do … end` — **a chip on a console's cartridge**, named where the consoles are, since it is part of what the cartridge is. `:superfx` gives the Super Nintendo cartridge a Super FX 2 board (`Cartridge::SNESROM::SUPER_FX`: slow LoROM, cartridge type $14, the chip's 64K of RAM at $70:0000), and the game's description its roomier limits (`Console::Variant`). `vblank build --console snes --variant superfx` (or `--variant none`) overrides it for one build; `game.program(console:, variant:)` and `game.build_rom(console:, variant:)` take one too. A variant a console does not have (`Console::Kit#variants`) is a friendly error naming the ones it has.
- `VBlank.game "NAME", consoles: %i[gba gbc], sprite_piece_size: { gbc: [8, 16] } do … end` — **the size a console draws a sprite's pieces at**, named by console, since each has sizes of its own (`Console::Kit#sprite_piece_sizes`). The Color draws every sprite from entries of its table, forty at once, and every entry is 8×8 unless the game says 8×16; then two 8×8 squares one above the other are one entry, so a figure stacked in halves (`image ..., pieces:` with each lower half 8 under its upper) takes half the forty. A square with nothing under it is an entry too, with an empty lower half, and counts on the eight rows under it toward the ten a row; a picture drawn rather than made of pieces is cut 8×16. It is one switch for the whole game. What the sprites show is the same either way, on every console. A console left out draws its first size (8×8). A size a console does not draw is a friendly error naming its sizes, and so is one for the Advance, which draws each sprite whole, or for a console the game is not for. `VBlank.build` and `Cartridge::Options` take it in the same form.
- `wait_vblank` — wait for the safe window to draw. A `game_loop` already does this each pass, so you only write it in a program that has no game loop, or under `frame_sync: :manual`.
- `halt` — stop (branch to self). `debug_halt` — truncate the ROM here (bisecting).
