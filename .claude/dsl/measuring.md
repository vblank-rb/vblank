# DSL reference: Measuring a finished game

The map of every page is `.claude/rules/dsl-reference.md`. **On this page** has a line for each
verb here; the entries after it tell each one in full.

## On this page

- `rom.profile` / `vblank profile game.rb` — where the frames went; `tape:, frames: 9..12` reads each (not GBA); `rom.sprite_memory`.
- `Diagnostics::Film.make "door.mp4", sides:, parts:, keys:` — an MP4 of 1 or 2 cartridges; `FilmTasks`: rake film.
- `Diagnostics::FilmShell.new(GAME)` — a port's shell as a film side from its first start: menu, LOAD ROM, the bar, the game; `#all_in_one` beside it.

## In full

Not verbs — these are called on the built cartridge.

- `rom.profile` (also `vblank profile game.rb`) — **what the build made of your game, then where its frames actually went.** Two halves. First the build's: how big each routine came out, which fit in the console's quick memory and which missed, what a routine that missed wanted and what was left when its turn came, what each layer holds, **which collections went in the roomier of the console's two work memories** (a decision nobody wrote, and the only way to see it), and **how much of the console's picture memory the sprites and tiles took — with how much of the room left over came from storing the small-palette ones at half size**. None of that survives into a running cartridge, so nothing else can tell you afterwards (least of all the last one: the pictures are there at the size the build chose, and what they would have cost the other way is gone). Then the run's: which of your routines the console really spent its frames in, the rate it produced (new pictures a second, one for each pass of the game loop), and how much of each frame was left over. Nothing here is predicted, so nothing here can be wrong about a loop nothing could see through. `format: :json` gives the same facts as data, for comparing two builds.
- `VBlank::Diagnostics::Film.make(path, sides:, parts:, keys:)` — **a film of a running cartridge, or of two side by side, as an MP4 a person can watch without running anything.** The same moment played on each side a frame at a time with the same buttons, every frame of the parts asked for shown at twice the console's size over a strip with each side's label and the frame's number, at sixty frames a second. What a test holds frame by frame, shown — two builds of one game, or a game beside the cartridge it is a copy of.

  ```ruby
  VBlank::Diagnostics::Film.make("door.mp4",
    sides: { "ours" => -> { VBlank::Diagnostics::Verifier.new(ours, frames: 0) },
             "reference" => -> { VBlank::Diagnostics::Verifier.new(theirs, frames: 0) } },
    parts: [1..90, 200..240],
    keys: ->(frame) { :left if frame < 60 })
  ```

  **`sides:`** is one side or more, each label (yours, written in the strip) to a lambda that opens a running cartridge whose NEXT frame is the film's first: a Verifier told to play no frames, or one a playthrough left standing at the moment worth filming (`VBlank.playthrough(...).play(rom).game`). The sides are opened one after another, so only one runs at a time. Film asks two things of what the lambda gives back, so an emulator of a game's own can be filmed too: `step(1, keys: mask)` plays one frame with those buttons down (`IR::Buttons.mask`, a bit each, the Advance's key order), and `screenshot(path)` writes the picture on screen as a PNG — `Verifier#screenshot` does that, and is there for anybody who wants one still. It is closed afterwards if it answers `close`. **`parts:`** are ranges of frames counted from one; every frame up to the last one shown is played, shown or not. **`keys:`** answers the buttons down on a frame: a name, a list of names, or nil. **The last frame of each part is held 0.8 s**, so a jump to the next part is seen, and **the last frame is held until the film is at least 3 s long.** A side's first frame is often the console's blank white, before the game has painted anything. It needs **ImageMagick** (`magick`, or `convert` on ImageMagick 6), which puts each frame together, and **ffmpeg**, which writes the MP4; both are looked for before any frame is played, and a missing one is `Film::MissingTool`, naming it and how to install it with `brew` or `apt`. `search_path:` says where to look (a PATH's folders), the process's PATH if left out. **`scale:`** is how many times the console's size each picture is shown at, 2 if left out. Friendly errors: `sides:` that is not a Hash of lambdas, `parts:` that is not a list of ranges of frames from 1, and a `scale:` that is not a whole number from 1. Worked example: `test/lowering/gba/vblank/diagnostics/test_film.rb`.
- `VBlank::Diagnostics::FilmTasks` — **`rake film NAME=door`: a game's films as small files, and the task that makes them**, so a game keeps no film tool of its own. The Rakefile names where the films are and the sides; it requires only rake, and the library, the game and the film are loaded when the task runs, so nothing a game builds needs ImageMagick or ffmpeg:

  ```ruby
  require "vblank/diagnostics/film_tasks"

  VBlank::Diagnostics::FilmTasks.new do |t|       # FilmTasks.new(:other_name) for another task name
    t.films = "films"                             # the film files (default)
    t.out = ".cache/films"                        # where each <name>.mp4 goes (default); keep it out of git
    t.libs = %w[lib test/support]                 # folders a film can require from by bare name
    t.requires = %w[my_game]                      # loaded before any film
    t.sides = { "ours" => -> { MyGame.build_rom }, "retail cartridge" => "baserom.gba" }
    t.console = :ps1                              # build each game to build for this console (its first if unsaid)
    t.lowering = "ruby"                           # show each side this way (the emulator if unsaid)
  end
  ```

  **A side** is its label and a cartridge: a path to any cartridge file (one VBlank built or one it did not, so two builds of a game can be filmed with no retail cartridge), a built cartridge, a game to build (what `VBlank.game` hands back), or a lambda answering any of them, called only when a film is made. Each opens in its console's own emulator (libmgba for the Advance and the Color, bsnes for the Super Nintendo, Beetle PSX for a PlayStation program; `Console::Kit#open_probe` chooses) with a save folder of its own, taken away when it closes (`FilmCartridge`), and its console gives the screen's size, so an Advance side, a Color side and a PlayStation side are filmed alike. A PlayStation program is filmed at the size it sets its screen to (320×240 for VBlank's builds), and silent (the build makes no sound yet); a picture that changes size partway is refused, naming the side and both sizes. A game to build is built once, not measured; a side that wants the measured cartridge gives `-> { GAME.build_rom }`. A Genesis cartridge cannot be filmed yet; its game played as a lowering can.

  **`console:` and `lowering:`** — `rake film NAME=door CONSOLE=ps1 LOWERING=ruby` says them for one film, over `t.console` and `t.lowering` (an empty one, `CONSOLE=`, says nothing); a side the film file names with its own keeps its own; `FilmCartridge.open(GAME, console: :ps1, lowering: "ruby")` is the same for a `Film.make` side. `console:` (`gba gbc snes genesis ps1`) is the console a game to build is built for, its first if unsaid; a built cartridge or a file is for one console already, and a side that names another is refused, saying which console the file is for. `lowering:` is how the game is shown (`Playthroughs::CommandLine::SHOWN_WAYS`): `emulator` (the default, the cartridge in its console's emulator), `ruby`, `js`, `native` or `interpreter`, which play the game itself (`Playthroughs::LoweredGame`), so a cartridge file is shown only in the emulator and only the emulator starts from a saved state. A lowering plays the game the cartridge holds (`built_for_computer?` false), and is held back the frames the console's cartridge takes to start (`FilmCartridge::CARTRIDGE_START_FRAMES`, measured), showing a switched-off screen meanwhile, so a cartridge side and a lowering side of one game show the same pass on the same frame. Friendly errors: an unknown console or lowering (before any side opens, listing the ones there are), `logic` (no picture), a console the game does not name, a file named as another console, a cartridge file or a saved state on a lowering. **A film file** (`films/door.rb`, `FilmScript`) is Ruby, so it can `require` what the game's tests use to reach a moment, with these words:

  ```ruby
  parts 1..90, 200..240                 # frames shown, counted from where each side starts
  hold :right, on: 10..80               # buttons down on a frame or a range; as many as needed
  keys { |frame| :a if frame == 210 }   # or any frame's buttons in Ruby; a Hash or a lambda works too
  start_from tape: "walk.tape"          # every side plays a tape from power-on first
  start_from state: { "ours" => "ours.ss1", "retail cartridge" => "retail.ss1" }  # or a state an emulator saved
  side "old", "builds/old.gba"          # a side of the film's own (or `side("ours") { ... }`), replacing one of that label
  side "ps1", GAME, console: :ps1, lowering: "ruby"   # ...built for that console, played that way
  scale 3                               # three times the console's size
  film sides: { ... }, parts: [...], keys: ->(frame) { ... }   # all at once, for a film written as a Film.make call
  ```

  Frame 1 is the first frame from power-on, the frame after the tape's last, or the frame after the state was saved. What `hold` and `keys` say of one frame are held together. A side's block may answer a cartridge already running at the moment wanted (anything with `step` and `screenshot`, as Film asks); it is filmed as it stands and cannot take `start_from`. `rake film` without `NAME=`, or with one that is not there, lists the films; a missing ImageMagick or ffmpeg stops it naming what to install. Friendly errors: a film with no `parts`, no side, a `hold` that is not buttons and frames from 1, `keys` that is not a block, Hash or lambda, `start_from` naming both or neither, a tape that counts passes or starts from a save, and a running side told `start_from`. `Verifier.new(rom, save_dir:)` and `Verifier#load_state(path)` are what a side is opened with. Worked examples: `test/lowering/gba/vblank/diagnostics/test_film_tasks.rb`, `test_film_cartridge.rb`, `test/all/vblank/diagnostics/test_film_cartridge_choices.rb`, and `test/lowering/ps1/vblank/diagnostics/test_ps1_film.rb`.
- `VBlank::Diagnostics::FilmShell.new(GAME, console: nil)` — **a port's shell filmed as a player first meets it**, for a game made from an original (`data_pack`). `#open` is a side of a film: the shell started for the first time with no pack kept, its menu, LOAD ROM chosen (A on the menu's second pass, as the shell check presses it), this machine's copy handed over, the progress bar filling while the copy unpacks, then the game, which the film's buttons reach (the menu does not see them). `#all_in_one` is the same game built all-in-one, a switched-off screen until the frame the shell's game began on (`#game_began_on`) and then its first pass, so the two games show the same pass on the same frame; list the shell's side first, since Film opens sides in order.

  ```ruby
  shell = VBlank::Diagnostics::FilmShell.new(GAME)
  VBlank::Diagnostics::Film.make("shell.mp4", sides: { "shell" => -> { shell.open }, "all-in-one" => -> { shell.all_in_one } },
                                              parts: [1..60, 1200..1500])
  ```

  In a film file: `side("shell") { SHELL.open }` and `side("all-in-one") { SHELL.all_in_one }`, with `SHELL = VBlank::Diagnostics::FilmShell.new(GAME)` above them. The shell is built with every copy hidden and played as Ruby, as `vblank run --shell` and the shell check play it. The copy is the one this machine names, so a machine that names none stops with `Original::NotSet`, whose words say how to name one; the copy and the pack the shell keeps stay in a folder of the side's own, taken away when it closes, so nothing of the copy reaches the film's folder but its pictures. **The unpacking keeps real time**: the film shows the bar as a player's window would, a frame's time apart at most, so the frame the game begins on depends on this machine's speed; give parts that reach past it. Friendly errors: a copy the shell refuses (`FilmShell::Refused`, in a player's words), and `#all_in_one` before the shell's side has shown the game. Worked example: `test/lowering/ruby/vblank/diagnostics/test_film_shell.rb`.
- `rom.sprite_memory` — **where every sprite's pictures went in the console's 32K of sprite memory, scene by scene**, with no emulator. `puts rom.sprite_memory` prints each scene's sprites (its own and the ones every scene shows) one a line, in the order their tiles start: the first tile and how many, where that is in the console's memory (`0x06010000` on a screen drawn from tiles), whether the run holds all the sprite's pictures or is rewritten as the game runs (one frame at a time, rooms several sprites take turns at, a painted picture, a pool's pictures sent the first time each is shown, or `by groups` for a sprite whose pictures are in a set of picture groups), the pictures, how many pieces a picture is cut into, and who else draws from the same run. A pool is one line with how many slots it has, and letters of text are listed as `text`. Each scene's runs add up to what it uses, the number the build checks against the 32K; `saved_by_sharing` is what sprites drawing from a run another already holds did not cost; and `own_from` is the tile a scene's own pictures start at, after the ones every screen shows: the tiles from there on are written again as the scene takes over.

  **A scene's picture groups follow its sprites** (see `picture_groups` in `sprites.md`): for each set, the tiles of its room and where that is; each group with its pictures, the bytes bringing it up copies, and the first tile of each picture's place, where pictures of groups never up together share a place; each set `up_together:` names with what its pictures come to; and the worst set, counting each group alone too. The worst set is the least room the groups could take, and the room is never less: more only where the pictures could not be fitted round each other any tighter. The groups of every screen are listed in each scene, with its sprites. A grouped sprite says `by groups`, and its `poses` give each grouped picture's place in the room.

  **When a scene does not fit, the build stops with `GBA::SpriteMemoryFull`, and `error.sprite_memory` is the same map of the last try**, so the scene that does not fit can be read and not only one that does. The build never got as far as working out each scene's least there, so `least_needed` is what the scene used. A scene with picture groups is told which set of groups up together needs the most, what their pictures come to and the biggest of them, and that it can use fewer or smaller pictures in those groups, or take that set out of `up_together:`. Worked example: `test/lowering/gba/vblank/diagnostics/test_picture_groups_memory_map.rb`.

  As data, each of `screens` has `scene`, `used`, `own_from`, `gaps`, `saved_by_sharing`, `sprites` and `picture_groups`, and each sprite `sprite` (nil for text), `count`, `pictures`, `first_tile`, `tiles`, `tiles_alone` (what one of them takes by itself: a room, for sprites taking turns at rooms), `address`, `pieces`, `poses` (each picture with the first tile of each of its pieces), `held`, `rewritten?` and `shares_with`; each set of picture groups `name`, `first_tile`, `tiles`, `bytes`, `address`, `groups` (each `number`, `pictures`, `bytes` and `places`), `up_together` (each `groups` and `bytes`) and `worst`; `to_h` carries the same for JSON. The interpreter has no sprite memory — it draws a sprite from its picture wherever that is — so this is the cartridge's alone. Worked example: `test/lowering/gba/vblank/diagnostics/test_sprite_memory_map.rb`.
- **On the Super Nintendo `rom.profile` says how many frames each pass took and where the time went** (and on the Sega Genesis and the PlayStation, the same), read from the running cartridge: how many passes in how many frames, the frame rate, which pass was slowest, how many passes took each number of frames, how much of the time the game was waiting, how many lines of the picture the tightest frame had to spare, and your routines and the runtime's by their share of the time, a copy to video memory charged to the line that started it. `keys:`, `settle:` and `frames:` count passes there, and `format: :json` gives the same as data. The report also says which frames from power-on the time was read over (`measured_frames`, counted as a tape counts them), so the same frames can be read one by one with a tape (next entry). **It names the slowest pass by its frames too** ("The slowest pass took 3 frames: pass 12, frames 250 to 252 from power-on"; `slowest_pass_frames`, a range counted the same way), so what one long pass spent its time on is one more call: `rom.profile(tape: tape, frames: result.slowest_pass_frames)`. A profile counts its passes from the one that ends its settling, so the slowest can be the pass just before the frames the time was read over. **On the Genesis it also says how many 8×8 tiles the build put in video memory**, of the 1471 there is room for: the tiles of the pictures every scene shows, and under that a line for each scene that brings tiles of its own in, with how many are there while it is up (`video_tiles`: `room`, `every_screen`, `by_scene`; nil for a game that draws from no tiles). The build refuses a game past the room and names the pictures that took the most; this is the count for a game that fits, so a scene can be seen nearing the room before it is refused.

  **On the PlayStation** the processor's time is counted in Beetle PSX from each instruction's fetch to the next, by its address, so a wait on memory or on the graphics chip lands on the instruction that waited; the game's routines are named from where its build put them, and the runtime's code by the label before it. The report adds one line the other consoles have no use for: **how long the graphics chip was drawing** (`gpu_share`, 0 to 1, of all the time measured). The chip draws a pass's rectangles and faces while the processor goes on, so its share is time beside the processor's, not out of it; where the processor had to wait for the chip, that wait is in the runtime's lines: `rt_draw_list_send_wait` (the list of drawing commands sent before is still going to the chip), `rt_draw_list_finish_wait` and `rt_draw_list_drawn_wait` (the pass's end, its picture drawn whole before it is shown), and `rt_gp0_port_word_wait` (a place's faces, which go straight to the chip's port: its queue was full). A line of the picture is 2152 of the processor's cycles, a frame 263 lines. **It also says how late each slow pass ended.** The passes that went to sleep inside the break between pictures that began while they ran, a few lines late, are said as the Advance's are (`late_passes`). And for every pass that took more than a frame, it says how many lines past the last break it ran, by the frames those passes took ("123 passes of 3 frames ran 7 to 45 lines past the last break between pictures"): the lines sooner it had to end to take a frame fewer (`lines_past_blank`, frames taken to the lines, in the order the passes ran). The lines are counted by the console's own line timer as the program runs (a few instructions a pass in every build, read only by the profile), not worked out. Worked example: `test/lowering/ps1/vblank/diagnostics/test_ps1_profile.rb`. `vblank profile examples/cube3d.rb --console ps1` shows the place routines (`__place_crate__face_drawing`, `__place_crate__point_turning`) and the runtime's face cutting (`rt_face_*`) on top.
- **`rom.profile(tape: tape, frames: 2070..2080)` — each frame of a tape read by itself, on the Game Boy Color, the Super Nintendo, the Sega Genesis and the PlayStation.** A profile adds every frame it measured into one report, and a game standing still or holding one button is rarely where it gets slow: a chain of bombs or three enemies on screen is. And a menu reads a press on the frame it goes down, so a button held from power-on is one press however long it is held, and never gets past a title that wants two. A tape (`played.tape`, `VBlank::Playthroughs::Tape.read`, or `Tape.parse` of a few lines) reaches that moment with the same presses on the same frames every time. The cartridge plays it from power-on, and each frame of `frames:` (a range, counted from 1 as the tape counts them) comes back as a `Diagnostics::TapeProfile::FrameReading`: `frame`, the `buttons` the tape held on it, `lines_spare` (the lines of the picture the game waited through), **`awake_share`** (how much of that frame the game did not wait through, 0 to 1), `passes_ended`, its busiest routines by share of that frame's time (`game` and `runtime`, three of each, or as many as `routines: 8` asks for, `TimeByRoutine::Spent`), and **`picture_held_by`**: nil when a new picture went up, `:pass` when the game's own pass was still running at the blank (do less in one pass), `:gap` when the pass had ended but the work after it — the runtime working out what changed and copying it to the console, a blank at a time — ran past the blank (change less of the picture at once), and `:setting_up` before the game loop. `result.frame(2075)` is one frame, `result.busiest` the frame the game was awake for most of, `result.held` the frames with no new picture, `new_picture?` asks one, and `format: :json` gives the same as data. The report says the busiest frame first, then a line a frame in plain words with its routines under it:

  ```
  Frames 43 to 46 of the tape: 0 of 4 showed no new picture.
  The busiest frame was 44: the game was awake for 82.8% of it.

  Frame 44 (nothing held): 26 lines to spare, awake 82.8%. A new picture went up.
    yours: 75.4% spin, 4.0% idle, 0.6% the game loop
    runtime: 0.5% the sprite table's copy, run from quick memory, 0.3% rt_upload, 0.2% rt_far_call_de
  ```

  A tape that presses A on frames 300, 450 and 600 and nothing else is five lines under the tape's three of heading (`299 -`, `1 a`, `149 -`, `1 a`, `149 -`, `1 a`). Each console's profiler is the meter `TapeProfile.play` measures a frame with: the Color's plays a measured frame an instruction at a time and counts its sleep (`GBCProfiler`, its lines to spare its share asleep of the frame's 154), the others read their emulator's time by address (`TapeProfile::ProcessorTimeMeter`). **The answer key is the profile standing still**, which says the frames it measured (`measured_frames`) on each of them: an empty tape over them gives its busiest routine, and its fewest lines spare or its share asleep. On the Super Nintendo and the Genesis the emulator runs the processor a little ahead of the picture when nothing makes it wait, so the frame that starts a long stretch of the game's work can count some of the next frame's time too, as the profile's sum does. Friendly errors: something that is not a tape, a tape of passes (`tape.in_frames_on(cartridge)` makes it a tape of frames), a tape recorded from a save or after a lead-in, `frames:` that is not a range from 1, and `keys:` or `settle:` beside a tape, which says the buttons and the start itself. The Game Boy Advance's profile refuses a tape: it cannot read a frame by itself yet, and reaches a moment with `scene:` or `from:` instead. **The same from the command line**, `vblank profile game.rb --tape t.tape --frames 590..610`, and **from a rake task a game gets for free**:

  ```ruby
  require "vblank/diagnostics/profile_tasks"

  VBlank::Diagnostics::ProfileTasks.new do |t|       # ProfileTasks.new(:other_name) for another task name
    t.tapes = "tapes"                                 # where TAPE=<name> finds <name>.tape (default)
    t.libs = %w[lib]                                  # folders the requires are found in
    t.requires = %w[my_game]                          # loaded before the cartridge is built
    t.cartridge = -> { MyGame.game.build_rom(console: :gbc) }   # a built cartridge, or a lambda answering one
  end
  ```

  `rake profile TAPE=roulette FRAMES=590..610` (TAPE= a name in `tapes` or a path; `FORMAT=json`; without TAPE= the profile standing still over `FRAMES=60`). The cartridge has to be one the library built, since the routines are named from its build's record. Like `FilmTasks`, it requires only rake, and loads the library and the game when it runs; a tape that is not there lists the ones that are. Worked examples: `test/lowering/gbc/vblank/diagnostics/test_gbc_tape_profile.rb` (a Color title that wants A twice, whose one heavy frame only presses reach), `test_profile_tasks.rb` beside it, and `test/lowering/snes/vblank/diagnostics/test_tape_profile.rb`.
- **The profile also says whether the PICTURE came out right**, which is a different question from where the time went, and there is one such question per screen. A game drawing straight into the picture the display is reading is asked whether it **tore** — how many rows went up before the game had finished them. A game on `screen :bitmap, tear_free: true` is asked whether it is **losing half its drawing**, which is that screen's own footgun: it keeps two pictures and shows them in turn, so a game that ADDS to what is already there (a dissolve, a trail, a plot filling in) puts half its additions in each and the screen alternates between two half-finished pictures. What the player sees is flicker, and nothing on screen explains it — every dot the program drew really was drawn. The report names how many pixels are stuck, where the first one is, and the two fixes: repaint the whole picture every frame, or use `keep_showing` for a part that changes now and then. A game is on one screen or the other, so exactly one of the two is ever asked, and a screen where neither applies says nothing rather than saying "no". **Both are measured on a real run, not read off the program** — which is the whole point, because the difference between a trail that is broken and one that is handled (wolf3d's death fizzle draws every dot on two frames running) is how many frames each drawing op runs on, and nothing at build time can see that.
- **The profile also says how many bytes the game COPIED INTO VIDEO MEMORY a frame, and what copied them** — tiles it paints from a list (`tiles ..., from: list` and `changed`), a whole map handed to a background (`show_map`), and a sprite kept to one frame at a time getting its next frame. Each is a copy in the gap between frames, and the processor waits while it runs, so the time lands on the routine that started it (see the next entry) and this line says what the copy was; a game typing a box of text can see what typing costs: a 104-tile run copied every frame says 3328 bytes a frame. It is counted off the console, from how many times the instruction that starts each copy ran, so nothing is added to the cartridge to count it. A kind of copy that did not run in the measured frames says nothing, and a game with none says nothing at all. A pool's pose copied in the first time one of its things shows it (see "A scene owns what it draws") is not in this line, since each pose is a different size and the count is of how often a copy started; its time is in the line of the routine that draws the scene's sprites.
- **Each routine's line gives two shares: of the instructions run, and of the time the console was awake**, and the two part company at a copy. The console stops the processor until a copy is done, so a routine that sends a scene's pictures as the scene arrives runs a dozen instructions and can take most of a frame. The time is charged to the instruction that started the copy, so it lands on the routine that asked for it. A copy the screen or the sound starts by itself (a background's rows bending, recorded sound being fed) is left out of that: its time lands on whatever was running.
- **The profile also says when a pass ended a few lines too late.** A pass of the game loop waits for the NEXT break between pictures, so a pass that ends two lines after a break began sleeps a whole picture, and a game whose rate halves for two lines of work otherwise shows only the lower rate. The report says how many passes did it and how many lines sooner they had to end, and `format: :json` carries the same as `late_passes`. A few kilobytes more of pictures sent on a scene's arrival is a handful of lines, enough to end that pass inside the break. A game none of whose passes ends late says nothing.
- **It also says when the screen updates after the wait ran past the next break.** On the Advance a game loop's pass begins with what the framework sends the screen as the wait ends (sprites, scroll, maps, colours, an area's tiles), and those belong to the break the wait woke in. Where they are still running when the next break begins, that picture is lost there, however many lines the pass has to spare when it goes to sleep, so the late-pass line above cannot see it. The report names each such pass by its number in the run and how many lines into that break the updates ended ("In pass 10, the screen updates after the wait ran 6 lines past the next break between pictures"), and `format: :json` carries them as `gap_overruns` (`pass`, `lines`). The line is read by the emulator as each pass reaches the end of those updates, at an address the build records (`rom.built.gap_ends`); nothing is added to the cartridge. A game whose updates all end in time says nothing.
- **Measured from power-on with no settling (`settle: 0`), the profile also says how close the FIRST pass came.** That pass holds everything the game sets up before its loop (up to the first wait for the screen, which is the loop's own unless the setting up waits itself), so it is the one a game makes longer each time it declares more, and it is on time until the day one more list tips it a whole picture later. The report says how many breaks between pictures it ran through (each a picture later for the first picture) and how many lines before the next break it ended, or how many lines into a break it ended where it was a few lines late, with how many lines sooner shows the first picture a picture sooner. Setting up still running when the measuring stops is said, with a word to measure more frames. `format: :json` carries it as `power_on_pass` (`missed`, `ended_before`, both null for one that did not end). A run that settles first says nothing, since the first pass it sees began before it did. In that run the setting up has its own line ("setting the game up, before the game loop"), and each `repeat` written in it (not inside a `func` or a scene) that pushes into a list has a line named after the first list it pushes into, so a hand-written fill loop that is most of the first frame says so. A second loop filling the same list counts as setting up. Worked example: `test/lowering/gba/vblank/diagnostics/test_profiler.rb`.
- **The profile also says which PART of a routine too big for the quick memory to make a `func` of.** A routine goes in the quick memory whole or not at all, so one that grows past the room — a game's play screen, most often — runs entirely from the cartridge, though most of its time is usually spent in a small part of it that would fit. The build does not take a game's routine apart on its own; the profile names the part instead, by the line of the game that wrote it: its share of that routine's time and of the frame's, how big its code is, and whether it fits — in the room the quick memory has spare, or in the room of routines kept there that the frame spent less time in, since the build chooses by time and a busier `func` takes their place. Where one statement and the block holding it have the same time, the smaller is named, and up to three parts that do not overlap are named for one routine. A part has to hold at least a twentieth of its routine's time and a hundredth of the frame's to be named, so a routine that missed and does next to nothing says nothing. It is measured rather than worked out, so it is about the run it came from: a part busy only in a boss fight is named only by a run of the boss fight. Worked example: `test/lowering/gba/vblank/diagnostics/test_split_hints.rb`.
- **The profile also says how many SOUNDS did not play.** `play` on a `sample` fills one of the mixer's voices, and with every voice busy the play is dropped — deliberately, since the alternative is cutting off a sound already sounding, which is worse and is never what anybody meant. So the game carries on, right in every other way, one sound quieter than you wrote it. A note of a song or a sound effect that finds no voice is counted too (see `sound_effects`). There is no error and nothing on screen, and no build can see it coming: whether it happens depends entirely on play — a burst of explosions, a chord of music underneath them. The report says how many were lost over the frames it measured, and — where a song was holding voices at the worst of those moments — **how the voices were being split**, which is the half you can do something about (a part moved onto the square wave, a shorter chord, fewer sounds at once). How many were *sounding* is never said, because a drop means every one of them was. A run that lost nothing says nothing, and a game that plays no samples says nothing either, so "we did not look" never reads as "nothing was wrong". It reports rather than warning: a game that fires twenty shots in a frame and hears sixteen sounds right, and whether the loss matters is a question about your game's sound that no count can answer.
- **The profile also says how many times a sprite was drawn in the WRONG COLOURS.** The console lends the groups of sprite colours left over to the lists things on screen wear (see `draw_with`), and with more lists on screen at once than groups to lend, the extra things are drawn in another list's colours. Nothing stops, and no build can see it coming, since it depends on what is on screen together. The report counts it over the frames it measured, each time one sprite on one frame (`colors_short` in the data form). A run that had groups enough says nothing, and a game whose lists all have a group of their own says nothing either.
- **Reaching the moment worth measuring is the whole problem**, because the interesting ones are the worst ones — the boss, the floor with sixty guards, the frame where a dozen things explode — and those are exactly the ones furthest from the title screen. A game boots to its title and **holding a button will not get past one**, because a menu reads the press *edge*, so a held button is one press however long it is held. There are three ways in, and the report always says which one it used, since the same cartridge measured on its title screen and measured in its boss fight are different numbers about different code.
  - `keys: [:left]` — held for the whole run. Worth passing wherever it helps: a game costs what the player makes it cost, so a profile with nothing held is a profile of a game standing still.
  - `press: [:a]` (`--press a`) — goes down as the measured frames begin, after `settle:`, and stays down. It is for a button the game reads as it goes down, a trigger or a bomb, which a button held from power-on never sets off.
  - `tape:` with `frames: 590..610` (`--tape`) — **presses on given frames from power-on, each frame of the range read by itself** (above). The way past a menu on the Game Boy Color, the Super Nintendo, the Genesis and the PlayStation, whose profiles take neither `scene:` nor `from:`.
  - `scene: :playing` — **hold the game in one screen and measure that**, with nobody playing it. Which screen a game is on is just a variable and the build knows where that variable lives, so it is written before every frame. Written once is not enough and that is not a detail: a game left alone *leaves* almost at once — put snake into its playing scene with nobody steering and the snake is dead in a few frames, so every scene reports the game-over screen's routines under the wrong name. Held there, it measures the routines that scene runs. It is not a game anybody could play, and it does not need to be.
  - `from: "boss.state"` — **measure a moment you played to**, saved as an emulator save state. This is the general answer and the one for a moment a scene cannot give: a scene says which routines *run*, where a saved moment also carries the **state that makes them expensive**. The boss scene with nothing spawned is not the boss fight. Play to it once, in any emulator, save, and profile that moment for ever after.
- **The build measures every scene the same way `scene:` does, standing still** — unless the scene says what to press. `scene :playing, measure_holding: %i[up b]` holds those buttons while the build measures that scene, and `measure_holding: tape` plays a tape's presses round (see `scenes.md`). That is what puts a fight's routines in the quick memory, where a scene measured standing still never runs them. The report says what each such scene was measured doing, under the quick memory, beside "chosen from a measurement of a real run". `rom.profile(scene: :playing)` itself holds only its own `keys:` and `press:`.
- **A state from a different build is refused, loudly.** A saved moment holds addresses, and rebuilding the game — changing one number — moves every one of them, so reading it would give numbers about whatever code took those addresses over. That still looks like numbers, which is what makes it worth an error rather than a warning: measuring the wrong thing quietly is worse than not measuring. The emulator will not catch this for you (it only refuses a state from a different *game*, by the title in the cartridge header, and accepts one from a different *build* of the same game), so the framework compares the cartridge's own checksum, which the state records. **A build is deterministic**, so this never becomes a nuisance: building the same source twice gives the same cartridge, and simply re-running a build keeps every saved moment. Only a real change moves the addresses, which is exactly when the moment has stopped meaning anything.
