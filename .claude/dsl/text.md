# DSL reference: Text & numbers

The map of every page is `.claude/rules/dsl-reference.md`. **On this page** has a line for each
verb here; the entries after it tell each one in full.

## On this page

- `draw_text "HI", x, y, color`, `draw_number :var, x, y, color, digits:` (`leading_zeros:`); `:left`/`:center`/`:right`.
- `text_width`, `text_height`; `font :name do glyph … end`; `pictures:`/`strip:`: no colour.

## In full

- `draw_text "HELLO", x, y, color` — fixed-origin text (`font:` picks a registered font; default `:default`). **A character the font does not have is a friendly build error** naming the character and the font, because the words are known while the game is built and a gap in a line otherwise shows only in the picture. `:default` holds the capitals (small letters fold to them), the digits, and the marks `! . : - % , ' ? / > <`; `:tiny` holds the digits and a space, so it is for `draw_number`. A space is the way to ask for a gap.
- `draw_text "SOUND", x, y, [:gray, :white], showing: picked == 1` — **two colours, and a test saying which**: the second while it holds, the first when it does not. A label that highlights, a HUD figure that turns red when the health is low (`showing: hp < 20`). Written the long way — the same words drawn twice, under a test and its opposite — it says the same thing and paints the same pixels, and it costs twice as much on **either** screen. On a **tiled** screen the console draws each character as its own little sprite out of a table of 128: two draws are two sprites for every character with one of them always hidden, where this is **one sprite that changes colour**, because the pair becomes two poses on it and the console is already swapping which picture a sprite shows for free. That halving is what lets an eight-row `menu` fit. On a **bitmap** screen the words are painted pixel by pixel into code, so two draws are every pixel of them twice over, where this **paints them once** with the colour picked by a test just before — a handful of instructions for the second colour rather than a second copy of the words. On the jukebox, whose song list is a menu of such rows, that takes about a fifth off its code. Exactly two colours: a test is 0 or 1 and a pair has a 0 and a 1, so the choice can never land outside it. Three is a friendly error saying to draw the text under a test for each, and a pair without `showing:` (or `showing:` with one colour) is a friendly error too.
- `draw_text name, x, y, :white, font: :thin, from: 0, length: 3` — **words held in a list**, on a painted screen: a name the player typed, a row of a high score table. `name` is a `list` of character codes (`name.push "A".ord`), and `from:` and `length:` pick a run of it, all of it when left out, so one list can hold ten names. It draws in any registered font, each letter at its own width, with no images of its letters, and `x` and `y` can be worked out as the game runs. A code the font does not have draws nothing and takes only the gap. Because the words are not known until the game runs, the left edge is a column rather than `:center`, there is one colour, and `within:` and `showing:` are friendly errors. **What it costs**: each letter is read out of tables as the game runs and each lit pixel is a rectangle of its own, so it costs far more than words written in the program, and a screen that only changes now and then wants it inside `keep_showing`. One routine is built for each list, font and colour however many places draw it. On a tiled screen, where each letter is a sprite made while the game is built, it is a friendly error: use a `canvas` and its `draw_letter`.
- `draw_number :var, x, y, color, digits: 3, font: :tiny` — a live number (right-aligned, no leading zeros). In a font of pictures it takes no colour: `draw_number score, 8, 8, digits: 5, font: :numerals` (see `font ..., pictures:` below).
- **Say where it goes instead of counting pixels**: where the left edge goes, both verbs also take `:left`, `:center` or `:right` — `draw_text "PONG", :center, 40, :white`. A number you write still means that column, and is still right when you actually want a column; what a number cannot be is CENTRED, because a proportional font has no per-character width to multiply by and the only thing that knows how wide "PRESS START" comes out is the font. Ask it and a label can be reworded with no stale number left behind. `within:` narrows what it is placed against — `within: 0..119` centres a caption in the left half, `:right, within: 0...120` pushes a label up against the middle from its left — and with no `within:` it is placed against the part of the screen an `inside` block is holding drawing to, else the whole screen, so a heading over a panel centres on the panel. A `draw_number` places its FIELD rather than the number in it, which is what stops a centred score jittering sideways as it counts up. Giving both a column and a `within:`, or a name the verb does not know, is a friendly error. Worked examples: `examples/pong.rb` (each score pushed against the net from its own half), `examples/jukebox.rb` (a menu column centred on its widest song name) and `examples/shmup/hud.rb` (a HUD flush against both edges).
- `text_width "SCORE"` / `text_height` (both take `font:`) — how wide a string comes out and how tall a line is, in pixels. Useful on its own for anything sized to fit words: a box behind a title, a menu window as wide as its longest row, the figures hung one gap off the end of their label. It is the same number on every screen, because every screen advances by each glyph's own width: a bitmap screen as it plots the pixels, a tiled one as it stands each character's little sprite. So a proportional alphabet stays proportional on `screen :tiled`. A live `draw_number` is the exception on both, and on purpose — each digit keeps a column as wide as the font's widest glyph, so a digit that changes never moves the ones beside it.
- **On `screen :tiled`** (no framebuffer) both draw each character as a little hardware-sprite glyph the console composites over the game. Same verbs/args, one rule: **declare them once — above `game_loop`, or inside a `scene`** (where they belong to that scene and show only while it's active), like a `sprite` — they're redrawn for you every frame and a live `draw_number` follows its variable and updates itself (so pass a variable, not a one-off expression). Declaring loose inside `game_loop` is a friendly build error. **A test around the declaration says when it shows**: `draw_text "PRESS START", 76, 100, :gray if blink == 1` is a blinking prompt — the condition rides onto the glyphs, so they are on screen exactly while it holds, and it is read again every frame like the rest of the HUD. That is one declaration, not a per-frame draw, so it is allowed above `game_loop` and inside a `scene` the same as a plain one (an `else` shows its text while the condition is false). Glyphs use one 8×8 sprite each, so the built-in `:default`/`:tiny` fonts fit; a HUD costs a few of the 128 sprites.
- `font :name do glyph "A", <<~ART … ART end` — define a font from glyph art (sibling of `image`); built-ins `:default` (5×7) and `:tiny` (3×5 digits). **Or hand it pictures of the letters** — `font :name, glyphs: { "A" => rows_of_pixels, … }, blank: 0` — for a font that already exists, sliced out of an image or decoded from a game's own data, because nobody is going to retype an alphabet as hashes and dots. A glyph is rows of pixel values and a pixel that is not `blank:` is lit, so which ink the picture used never matters; each glyph keeps its **own width**, so an alphabet drawn proportionally stays proportional. Give a block or `glyphs:`, not both. On `screen :tiled` the console draws each character as one 8×8 sprite, so an imported alphabet can be too big for it — a friendly error names the widest character.
  **An alphabet in a data pack**: `font :lettering, glyphs: { "A" => pack[:font].pixels(0, 70), … }, height: 10` — each letter a run of a slot of pixels, one byte a pixel, row by row, `height:` rows (so its width is its count over the height), lit where the byte is not `blank:`, written in the colour `draw_text` asks. Built with the pack read (every cartridge, and a computer build all-in-one) it is a font of glyphs like any other. With the pack left out (`pack_at_start:`) each letter is a picture of the pack's pixels in each colour the game writes in, filled as the game starts: it costs a copy of the letters' pixels for each colour, a number that changes needs all ten digits, which may differ in width (a number is laid out as the all-in-one build lays it out: each digit at the left of a column as wide as the font's widest letter, and a place not reached left empty), and words from a list of character codes cannot be drawn in it. Friendly errors: no `height:`, a letter that is not whole rows of it, `fold:` or a list of codes with the pack left out.
- `font :numerals, pictures: { "0" => :zero, "1" => :one, … }` — **a font made of the game's own pictures**, each character a picture declared with `image`, in as many colours as it has: a score in the game's own numerals, words in letters lifted off a cartridge. The pictures can be art, a file, or made from a data pack's tiles (`image :zero, width: 8, height: 8, colors: pack[:palette], places: pack[:digits].tile(0)`); ten in a row is `("0".."9").to_h { |d| [d, :"digit_#{d}"] }`. Each picture keeps its own width, so letters can be proportional; all must be one height. `spacing:` is the gap between characters, 0 unless given, since a picture carries its own margin.
- `font :numerals, strip: :numeral_strip, characters: "0123456789 "` — **the same font cut from one strip**: one picture of the characters side by side, cut into equal pictures, one for each of `characters:`, left to right, the way an original keeps its numerals. The strip can be art, a file, or a picture from a data pack. One of a pack's tiles (`places: pack[:digits].tiles(0, across: 10)`) is cut by its tiles, so it must be one tile tall and each piece a whole number of tiles wide. One of a pack's pixels (`places: pack[:bar].pixels(first, 88 * 16)`, one byte a pixel) is cut at any width, and so is one that holds its own places and takes its `colors:` from the pack. With the pack left out (`pack_at_start:`) the build holds none of the strip's pixels, so each piece reads its own part of the pack as the game starts, and draws what the all-in-one build draws; a strip that cannot be read that way (a `mirror` or `upside_down` of a picture from the pack, or a pose that is a frame of the original) is a friendly error there, naming `pictures:` as the fix. A strip whose width does not cut into that many pieces is a friendly error.
- **Drawing in it**: `draw_text "GAME", 8, 8, font: :numerals` and `draw_number score, :right, 4, digits: 5, font: :numerals` take **no colour**, since the pictures have theirs. A colour or `showing:` beside such a font is a friendly error, and so is leaving the colour out with any other font. Everything else is what the two verbs do in any font: `digits:`, right-aligned with leading noughts dropped, `:left`/`:center`/`:right` and `within:` placing the field, each digit in a column as wide as the widest picture, a live number on a tiled screen following its variable. `text_width` and `text_height` measure it.
- **The space**: a font that has a `" "` picture draws it for a space in words and for each leading nought. It paints over the digit that was there, so a number on a screen that is not cleared each frame needs no clearing of its own. Without one, a leading nought draws nothing.
- `draw_number minutes, 8, 8, :white, digits: 2, leading_zeros: true` — **noughts in every place**, as a clock writes 07, in any font: the glyph for 0, or a picture font's "0" picture.
- **What a picture font refuses**, each a friendly build error: a character the font does not hold (as in any font); a live `draw_number` in a font without all of 0 to 9 at one size (the space too, at that size); a picture the font names that is not declared; pictures of two heights; a list of character codes.
- **What it costs**: a character is its picture drawn the plain way, a `blit` on a bitmap screen and a sprite on a tiled one, so every console already draws it and nothing is built for a game that declares none. On a bitmap screen a live number's place is one of ten pictures picked by number, which is a test and a copy for each; so the places of all the font's numbers call one routine that draws it, written once. The first live number costs about what one place written out costs, and each number after it less than a live number in the built-in font. On a tiled screen each place is one sprite whose pose is the digit, so a five-digit score is five of the 128. On a tear-free bitmap screen each picture follows `blit`'s rules: an even column and an even width.
